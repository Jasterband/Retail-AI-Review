# 技术选型与数据存储

> AI 审核服务侧已定方案（与 PE 业务库分离）。

---

## 1. 已定技术栈

| 项 | 选择 | 说明 |
|----|------|------|
| API 框架 | **FastAPI** | 实现 [README-PE-simple对接.md](README-PE-simple对接.md) 中的 `/v1/retail_meeting_checks`、`/health` 等 |
| 本地数据库 | **SQLite** | 本机开发、单文件、零运维 |
| 部署数据库 | **PostgreSQL（AWS RDS）** | 上 AWS 后切换；可用同一套 SQLAlchemy/ORM 模型 |
| 数据库职责 | **仅存 AI 侧数据** | 不存 PE 会议主数据；PE 通过接口拿最终结果自行落库 |

连接串用环境变量切换，例如：

```text
# 本地
DATABASE_URL=sqlite:///./retail_meeting_check.db

# AWS
DATABASE_URL=postgresql+psycopg://user:pass@xxx.rds.amazonaws.com:5432/retail_meeting_check
```

## 2. 存什么：中间结果 vs 最终结果

本库专门服务 AI 审核，分两层：

```text
PE 提交 RetailMeetingCheckRequest
        ↓
   写入任务 + 请求快照
        ↓
   跑规则过程中 → 不断写入「中间结果」（debug）
        ↓
   汇总完成 → 写入「最终结果」（对外）
        ↓
PE 查询 / 回调 ← 只读最终结果（RetailMeetingCheckResponse）
```

| 类型 | 给谁用 | 存什么 | 怎么拿 |
|------|--------|--------|--------|
| **最终结果 · simple** | PE / 线上展示 | 最瘦：`overall_status` + 每张 `photo_status` + `fail_reasons[].reason_code`（无文案 / 无 `rule_results`） | 默认：`GET ?mode=simple` / 回调 |
| **最终结果 · full** | AI 排障 | 落库完整形态：`checks`、OCR、detections、evidence、`rule_results`、`debug` 等 | `GET ?mode=full`（或提交 `options.response_mode=full`） |
| **中间结果** | 更深排障 | 逐步日志、超大原始 JSON、临时 crop 路径等 | 库表 `ai_step_log` / `ai_artifact`；full 可带 `artifact_refs` |

> 服务端始终落**完整**最终结果；`simple`/`full` 只是查询/回调的**投影**。中间大文件仍建议只进 artifact 表，不必整包塞进响应。

### 2.1 最终结果（建议表）

对应原设计中的 AI 表（可只建 AI 库，不必建 `pe.*`）：

| 表 | 作用 |
|----|------|
| `ai_check_job` | 一次材料检查任务：`task_id`、状态、`pe_snapshot`、最终 `overall_status`、完整响应 JSON |
| `ai_asset_result` | 每张材料最终摘要；API 响应数组名为 `photo_results` |
| `ai_rule_result` | 每条规则的最终判定（给 PE 看的那版） |
| `image_dup_history` / `topic_history` / `template_ref` | 跨会照片指纹（pHash/embedding）；讲者主题历史；模版参考 |

`ai_check_job` 建议增加字段：

- `final_response_json`：完整 `RetailMeetingCheckResponse`，查询接口直接读出  
- `finished_at`：终态时间  

### 2.2 中间结果（建议表，debug）

| 表 | 作用 |
|----|------|
| `ai_step_log` | 流水：job 下第几步、步骤名（`download`/`ocr`/`logo`/`panorama`…）、开始结束时间、成功/失败 |
| `ai_artifact` | 中间产物：关联 job + asset；类型如 `ocr_raw`、`detections`、`model_raw`、`crop_debug`；内容放 JSON 或 S3 路径 |

示例字段（示意）：

```text
ai_step_log
  id, job_id, step_name, status, started_at, finished_at, message, detail_json

ai_artifact
  id, job_id, photo_id(nullable), artifact_type, payload_json, s3_uri(nullable), created_at
```

保留策略：中间结果可设 TTL（如 30 天）或仅保留 `FAIL`/`NEED_HUMAN`/`ERROR` 任务，避免盘爆。

## 3. 和 PE 的边界

| 数据 | 在哪 |
|------|------|
| 会议、讲者、状态机、AI 校验次数展示 | **PE 库**（PE 系统） |
| 请求快照、审核过程、最终 RetailMeetingCheckResponse | **AI 库**（本服务） |
| 照片文件 | **S3**（PE 写，AI 读） |

PE **不需要**直连 AI 的 SQLite/RDS；只调 HTTP 拿最终结果。

## 4. FastAPI 模块建议（落地时）

```text
app/
  main.py              # FastAPI 入口
  api/retail_meeting_checks.py        # POST/GET /v1/retail_meeting_checks、/health
  schemas/             # 与 docs/schemas 对齐的 Pydantic
  db/                  # engine：SQLite / Postgres 切换
  models/              # job / rule_result / step_log / artifact
  services/
    check_runner.py    # 异步跑规则，写中间结果 → 写最终结果
    s3.py
    rules/             # 各 rule_code
```

提交接口：校验 → 插入 `ai_check_job`（RUNNING）→ 投递后台任务 → `202`。  
查询接口：读 `final_response_json`（或 RUNNING 占位）。

## 5. 两类跨会议查重（分开）

每次 PE 只传本场；历史不在请求里。

**A. 照片重复（盗用他场 · 图像 · 跨会议）**

1. 对本场 **每一张照片** 算 **pHash / embedding**  
2. 只查 AI 库 **`image_dup_history` 中其他会议**（排除当前 `meeting_id`）——**不查会内**相似  
3. 越阈 → `IMAGE_DUP` FAIL；结束后指纹入库  

**B. 主题/标题重复（文字 · 仅讲者照）**

1. 对 **`SpeakerTitle`** OCR 标题 → 归一化  
2. 与 **`topic_history`** 字符串比 → 命中则 `TOPIC_REUSE` FAIL  
3. 结束后标题入库  

详见 [检测点清单与photo_results.md](检测点清单与photo_results.md) §4。
